# 需求补全清单 v1.1

**日期：** 2026-10-30
**依据：** 《4.0规则引擎重构方案：专家评分与模拟状态转移规则》v1.0 及 2026-10-30 全项目对照检查结论。
**范围：** 上一轮检查识别的 11 项"尚未满足或存在偏差"需求（R1–R11）及 3 项确认点收敛。
**约束：** 全部为增量补全，不改动已验收的核心合同（专家只评分、状态引擎唯一写入、教师评分 0–100 与动态状态 0–1 分离）；`fin_ver` 与 `noreset` 必须保持同规则、同系数、同配置。

---

## R1 移除旧版独立打分算法（对应方案 §10.1、§14.3）

- **缺口：** `src/orchestrator.py` 的 `EnhancedEvaluator.evaluate_intervention()` 保留关键词打分（0–1 口径、0.6/0.4/0.2 阈值直接写 `bullying_intensity`），经 `src/__init__.py`、`runner.py`、`round_robin_runner.py` 仍可调用。
- **需求：** 教师干预质量评分全项目只能有一个实现入口（`InterventionExpertAgent`）。`EnhancedEvaluator.evaluate_intervention()` 删除全部关键词加减分与阈值写状态逻辑，降级为纯适配器：输入教师话语+完整对话上下文，输出与 `InterventionAssessment.to_dict()` 一致的结构（0–100 分、七维、风险、`assessment_status`）；无 LLM 时返回 `status=pending`，不得回退关键词打分。
- **边界：** 适配器不得输出 0–1 质量分、不得写任何动态状态。
- **验收：** 全库无第二套教师打分实现；相同干预经 CLI 与 Web 入口得到一致的 `final_quality_score_100`；无 LLM 时返回待评估且状态不变。

## R2 旧 CLI 显示与阈值口径迁移（对应 §10.3 第 4、5 条）

- **缺口：** `src/runner.py` 第 383 行 `quality_score:.0%` 显示、第 389 行 `>=0.5` 判断；`round_robin_runner.py` 第 436 行 `:.0%`。
- **需求：** 所有教师质量分输出统一为 0–100 数值格式（如 `75/100`）；基于质量分的分支判断改用百分制分档（40/60/80）。0–1 动态状态的百分比显示不受影响，但二者不得共用格式化函数。
- **边界：** `quality_score=None`（待评估）时输出"待评估"而非 0。
- **验收：** 75 分干预经 CLI 输出 `75/100`，绝不出现 `7500%`；教师评分的比较常量均 ≥10 或为 K 值。

## R3 风险评估证据与元数据完整保留（对应 §4.2、§5.3）

- **缺口：** `intervention_expert.py` 的 `_parse_and_validate` 将 `risk_assessment` 重建为 `{level, flags}`，丢弃原文证据、语境、置信度。
- **需求：** `risk_assessment` 完整保留逐项明细 `flags_detail: [{code, evidence, context, confidence}]`；level 仍由程序按 flags 数量重算并保留"取更严重"覆盖；明细随 `to_dict()`、干预返回体、日志全链路透出。
- **边界：** 非法 flag 过滤后为空则 level=none；单条风险缺证据时保留标记但 `confidence=0` 并标注"无证据"；空证据不得作为 serious 定级唯一支撑。
- **验收：** 注入 2 项风险的 mock 专家返回，每个 flag 均含 evidence/confidence；返回体中可审查风险原文证据。

## R4 预测效果与实际效果分开存储（对应 §15.1、§10.4、§14.3-1）

- **缺口：** 干预记录仅存实际前后差且沿用旧字段名，无 `predicted_*` 字段，无版本标记。
- **需求：** 每次有效评分的干预产生成对记录：
  - 预测：`predicted_effect_profile`（各内部状态目标、预期 delta、rule_id/K_eff/M4/门控依据）、`predicted_bullying_reduction`、`predicted_distress_change`，由 StateTransitionEngine 写入前从已聚合提案导出；
  - 实际：`actual_bullying_reduction = before − after`、`actual_distress_change = after − before`（带符号）。
  - 旧字段 `bullying_reduction`/`distress_reduction` 重命名为 actual 语义并与 R11 单位标记统一变更。
- **边界：** `pending` 干预不产生 predicted/actual（为 null，不入均值）；观察窗口为下一完整轮并记录起止轮号；实际变化归因不得全部记给教师分数，须引用同轮事件来源。
- **验收：** 跨 60/40 阈值回放，predicted 与 actual 分别存储；predicted ≠ 旧阈值查表值；actual 与 transition_log 前后差一致。

## R5 状态变更日志补全（对应 §10.5、§14.6、§15.2）

- **缺口：** `transition_log` 缺 `event_id、assessment_id、turn_id、风险门控结果、predicted_effect_profile、observed_effectiveness`；sources 无 event_id；`assessment_id = session_r{round}` 同轮多干预冲突。
- **需求：** 每条状态写入日志至少含：`session_id、turn_id、event_id、assessment_id（学生轮为 null）、source_role、target_state、state_before、proposed_deltas（逐条含 event_id/rule_id/source/evidence/confidence/risk_flags）、risk_gates（被抑制或触发的规则，suppress 提案留痕）、applied_delta、state_after、capped、predicted_effect_profile、observed_effectiveness、status、calibration_version`。
- **边界：** `assessment_id` 改为 `session_r{round}_i{干预序号}`，提案 event_id 携带 assessment_id；去重仅按 (event_id, rule_id, target_state)，同轮第二次干预的合法提案不得被吞。
- **验收：** 任取一条日志能回答"哪个事件、哪条规则、哪个提案造成哪个状态变化"；高质量+严重风险回放可见被抑制的 D2 正向提案；同轮两次干预各自生效且 ID 不冲突。

## R6 受害者/旁观者 Agent 读取完整状态（对应 §9.2 末段）

- **缺口：** `VictimAgent` 只读 `victim_distress`；旁观者 Agent 未读 `bystander_support`、`retaliation_risk`。
- **需求：** VictimAgent 决策输入至少含 `victim_distress、victim_safety、retaliation_risk` 及最近支持/暴露事件，输出新增 `reaction_tendency`（退缩/求助/感谢/反驳/沉默）；BystanderA/B 输入至少含 `bystander_support` 与 `retaliation_risk`。倾向经学生事件识别进入提案，不直接写状态。
- **边界：** 状态缺失按 0 处理；安全高但报复风险高时以风险优先；Agent 模块不得对动态状态赋值。
- **验收：** distress 相同、safety/retaliation 不同的两场景决策倾向不同；旁观者在 bystander_support 高低下决策不同；静态检查 Agent 无状态赋值语句。

## R7 干预残余效应衰减机制（对应 §8.3）

- **缺口：** 无独立残余效应存储；保留比例（0.55/0.80/0.90）未使用；现有 `INTERVENTION_RESILIENCE` 阻尼与方案残余机制概念重叠。
- **需求：** 会话级新增 `immediate_stop_residual`（D1）、`support_residual`（D2）、`norm_residual`（D5），初值=对应 K_eff；每完整轮无新增支持证据按保留比例衰减（配置化）；新攻击立即清零对应残余；残余参与下一轮 p_attack 与 Agent 倾向，不直接改动态状态。落地后 `INTERVENTION_RESILIENCE` 阻尼合并/移除，同一影响不得重复计入。
- **边界：** 已落实保护（victim_safety 已提升部分）不随残余回退；未到期跟进按待办管理不衰减；自然恢复/耦合/低强度减压仍走统一聚合与单轮上限。
- **验收：** 单次制止后残余按 0.55^k 递减且日志可读；制止后新攻击使残余立即归零；无衰减/统一轻衰减/按机制衰减可通过配置切换回放对比。

## R8 内部状态轨迹入库（对应 §6.1）

- **缺口：** `metrics_history` 仅存派生 B；`get_internal_states()` 无调用方。
- **需求：** 每轮 `_evaluator_logic` 结束将内部状态全量快照（九项内部状态 + R7 残余值）追加至 `internal_state_history` 并随会话 log_json 持久化；Web 状态接口与报告增加内部状态输出。
- **边界：** 新字段为增量，前端既有图表不受影响；教师干预轮同样写快照。
- **验收：** 回放 N 轮后可按轮检索完整 F/S/P 轨迹；每轮 B == round(0.40F+0.35S+0.25P, 4)；log_json 中包含内部状态历史。

## R9 规则引擎验收测试（对应 §11、§14.7）

- **缺口：** 仅有 API 冒烟测试，方案两表所列情境无自动化覆盖。
- **需求：** 建立不依赖真实 LLM 的验收测试集（专家评分用固定 mock 注入），覆盖 §14.7 八项与 §11 十一项情境；断言只针对方向、分档、上限与结构，不断言未校准系数；双入口测试文件完全一致。
- **边界：** level=2/3 标准脚本下合格干预序列可在合理轮数内触发"调解成功"（校准目标断言，不锁死数值）。
- **验收：** 测试集可一键运行且全部通过；作为后续规则改动的回归门槛。

## R10 参数配置化（对应 §6.3、§6.4、§14.5）

- **缺口：** 单轮上限、K/M4 分段、各维 max_delta、风险 delta 与 suppress 集、p_attack 系数、收敛四阈值、衰减比例均硬编码；yaml 无对应段。
- **需求：** 上述参数全部移入 `orchestrator.yaml`（`state_transition:`、`dimension_effect:`、`risk_rules:`、`agent_decision:`、`convergence:`、`residual_decay:` 段），代码仅读配置并保留与现默认一致的 fallback；`calibration_version` 随配置变化更新；启动时校验非法值。
- **边界：** 配置缺省时行为与当前默认逐项一致；`fin_ver` 与 `noreset` 配置文件除入口差异外必须一致。
- **验收：** 修改 yaml 上限后回放提案按新上限截断；双入口配置 diff 仅允许入口相关差异。

## R11 评分单位显式合同与数据迁移（对应 §14.4、§15.6 第 1、2 条）

- **缺口：** `js/app.js` 以 `0 < quality_score <= 1.0` 猜测单位（真实 1/100 会被误判为 100）；DB 旧 0–1 记录与新 0–100 记录同字段共存、无版本标记与迁移函数；pending 干预落库 `quality_score=0.0` 污染统计。
- **需求：** 所有教师评分记录增加显式单位字段 `quality_score_scale: 100`；提供一次性幂等迁移函数升级历史 0–1 记录并写入迁移标记；前端按 scale 渲染、删除启发式换算；pending 存 `null + assessment_status="pending"`；统计接口将 null 定义为"剔除"并写入约定。
- **边界：** 迁移幂等（重复执行不二次乘 100）；脏数据（负值、>100）记入迁移报告不猜测；迁移不影响 0–1 状态类字段。
- **验收：** 旧记录 0.75 显示 75/100；新记录 1 分显示 1/100；待评估干预不进入均值；全库无 `<=1.0` 式单位猜测代码。

## R12 干预发送反馈机制（用户可感知「已成功发送」，避免重复操作）

- **缺口：** 发送干预后仅有一行 `✅ 干预已发送` 文本，且 1.5 秒后被下一轮「对话生成中」覆盖；请求处理中按钮仍可点击、无进行中提示；失败仅用 `alert` 弹窗，用户无法判断干预是否已被服务端接收，易重复发送产生重复干预。
- **功能范围：**
  1. **三种可区分状态**：`sending`（发送中）/ `sent`（已发送）/ `failed`（发送失败），并以不同底色（琥珀 / 绿 / 红）与文案呈现；`duplicate`（服务端判定为重复发送）另用蓝色区分。
  2. **常驻状态条**：`#intervention-send-status` 独立于会被覆盖的 `#intervention-status`，成功信息（时间、评分、内容摘要）持续可见。
  3. **即时反馈**：点击后立刻进入发送中态——按钮改为「⏳ 发送中…」并禁用；超过 8 秒未返回提示「仍在处理（专家评分中），内容已提交，请勿重复发送」。
  4. **消息内标记**：教师干预气泡带「✅ 已发送 HH:MM:SS」标签，便于在对话区直接确认。
  5. **失败反馈**：不使用阻塞式 `alert`；改为状态条 + 状态区提示「❌ 发送失败：原因」，并明确「输入内容已保留，可直接重试；若长时间无响应请先查看对话区确认是否已发送」。
  6. **幂等保护**：客户端为同一内容生成并复用 `client_token`；服务端按 (session_id, token) 缓存 180 秒，重复提交返回首次结果（`send_status=duplicate`）且不新增干预记录、不重复写入消息。
- **输入输出：** 接口 `POST /api/session/{id}/intervene` 新增可选字段 `client_token`；响应新增 `send_status`（sent/duplicate）、`sent_at`、`content`、`content_chars`、`intervention_count`、`duplicate`。
- **边界条件：** 空内容仍返回 400 且不产生干预；待评估（评分 null）不影响发送成功判定，只影响评分展示；`client_token` 缺失时不做幂等（兼容旧调用）。
- **验收标准：**
  1. 首次发送返回 `send_status=sent` 且含 `sent_at`；
  2. 同一 token 重复提交返回 `send_status=duplicate`，会话中仅一条干预记录、消息不重复；
  3. 不同 token 视为新干预；空内容返回 400；
  4. 浏览器实测三态渲染正确（底色与文案可区分），发送中按钮禁用且文案变更，失败后输入内容保留可重试。

## R13 评分可解释性与封顶提示准确性（源自 2026-10-30 评分复核分析）

- **缺口：** ①原始均分本就低于 60 时，反馈仍显示「⚠️ 严重风险，总分封顶 60（原始均分 47.1/100）」，而封顶实际未改变任何数值——用户据此容易误判「被规则扣分」；②会话日志只保存维度汇总文本与专家总结，**未持久化**每维证据/理由/置信度与风险 flags 明细，事后无法逐项复核失分依据。
- **功能范围：**
  1. `apply_risk_cap()` 的 `cap_applied` 语义修正为「封顶实际生效」才为 True（`raw_mean > 60`）；分数计算逻辑不变，历史分数不受影响。
  2. 反馈文案区分两种情形：`capped=True` → 「严重风险，总分封顶 60（原始均分 X/100）」；`serious` 但未封顶 → 「存在严重风险（原始均分 X/100，本身已低于 60，封顶未额外扣分）」。
  3. 干预记录持久化完整 `assessment`（七维分数/分档/证据/理由/置信度、风险 flags 明细、`raw_mean_score_100`、`final_quality_score_100`、`risk_cap_applied`、`risk_level`），随会话日志与数据库落盘。
- **边界条件：** 不改变任何历史分值；`pending` 干预不产生 assessment；数据库旧记录无 assessment 字段时按缺失处理，不回填猜测值。
- **验收标准：** ①原始均分 72.5 + serious → 封顶 60 且 `cap_applied=True`；②原始均分 47.1 + serious → 分数不变且 `cap_applied=False`、反馈不再出现「封顶 60」；③高均分 + serious 仍如实提示封顶（回归测试 `tests/test_risk_cap_semantics.py` 8 项）。

## R14 用户指导机制（最终报告详细改进意见 + 逐轮分析 + 实时指导 + 连续低分预警）

- **缺口：** ①最终报告只有总体建议（策略类型、好/中/差计数），缺逐轮诊断与针对性改进意见；②模拟过程中除分数外没有任何指导，用户只能等到报告才知道问题在哪；③连续低分无提示，容易连续犯同类错误。
- **功能范围：**
  1. **逐轮分析（最终报告）**：报告新增 `round_analysis`，逐轮给出「情境概括 → 你的干预 → 评分与分档 → 失分维度（含失分依据与改进动作）→ 风险标记 → 下一步建议」；未干预的轮次同样给出指导。
  2. **详细改进意见（最终报告）**：报告新增 `improvement_suggestions`，含总体诊断、维度缺口（按「拉低总分的贡献」排序）、优先改进项 Top3（原因+改法+避免项+参考话术）、可直接套用的话术、需规避的风险清单、可勾选的改进行动计划；文本报告同步输出。
  3. **实时指导**：干预发送成功后立即返回 `coaching`（本轮得分与分档、最需改进维度及其改法、风险提醒、参考话术、七维分数表、写作清单），前端在干预面板展示指导卡片。
  4. **写作提示（预防性）**：进入干预输入时展示四要素清单；若上一轮有失分点或风险，额外给出「上轮重点补强」「规避风险」提示。
  5. **连续低分预警**：同一会话内连续 3 轮干预评分低于 60 分时，接口返回 `low_score_alert`（连���轮次、主要失分维度诊断、2–3 条可执行调整动作、可直接套用话术），前端以醒目横幅展示并同步插入对话区系统提示；任一轮达到 60 分即清零连续计数。

## R15 指导门槛与评分校准（对 R14 的修正，2026-11-05）

## 附：模拟结束机制核查结论（2026-11-05）

- **结束机制构成（本次核查未发现结构性改动）**
  1. 图内终止 `supervisor._check_termination`（每轮判定）：①调解失败——`victim_distress ≥ 0.95` 连续 3 轮；②超时——`round ≥ max_rounds`（默认 40）；③调解成功——连续 3 轮同时满足四条件：`attack_frequency<0.20`、`victim_safety≥0.70`、`retaliation_risk<0.30`、`follow_up_status≥0.50`，且 `round ≥ min_rounds`；④干预持续有效路径——`intervention_effective_rounds ≥ 4` 且四条件成立。

  3. Web 自动结束 `session_manager.check_auto_end_conditions` + `AUTO_END_CONFIG`，与图内同源，并可通过 `PUT /api/session/{id}/auto-end-config` 在线调整。
  4. 阈值来源：R10 已把四条件与 partial 阈值搬入 `orchestrator.yaml` 的 `convergence:` 段，**缺省值与原硬编码完全一致**（0.20 / 0.70 / 0.30 / 0.50 / 10 / 0.30）。
- **结论一：机制本身未被改动**，改动只发生在「驱动它到达阈值的输入」：
  - R7：移除 `INTERVENTION_RESILIENCE` 韧性阻尼，改为残余效应（0.55/0.80/0.90 衰减、新攻击清零）→ 干预效力随轮次衰减，攻击回升更快；
  - R15：无意义内容判 0 分 → `K_eff=0` → 不再产生任何状态改善（此前 ~30 分会给微小下降）；
  - R15 提示词锚点：评分整体下移 → `K(s)`（40 分以下直接为 0、40–59 为 0.20–0.485、60+ 为 0.50+）与 `M4`（D4<60 时 0.50）双重收窄了状态增量。
- **结论二：成功判定的可达性对干预质量高度敏感（实测，每轮干预一次）**
  | 干预分档 | 终止结果 | 结束轮次 | 未达标的条件 |
  |---|---|---|---|
  | 71.7 分 | success（调解成功） | 20 | — |
  | 49.4 分 | timeout | 40 | `victim_safety=0.59`（需 0.70）、`follow_up_status=0`（需 0.50） |
  | 38.7 分 | timeout | 40 | `victim_safety=0.31`、`follow_up_status=0` |

## R17 评分服务可用性与「提示卡面完全失效」根因修复（2026-11-05）

- **现象：** 用户反馈干预提示卡面完全未生效。
- **根因链（逐层定位，非推测）：**
  1. **密钥从未被加载**：`llm_client.get_api_key()` 只查 `<项目根>/.env`，而实际 `.env` 位于 `<项目根>/web/.env`；且该文件带 UTF-8 BOM，手工解析得到的键名为 `\ufeffMINIMAX_API_KEY`，被允许列表拒绝 → 密钥为空。
  2. **环境变量来源缺失**：`get_api_key()` 的环境变量分支只认 `DEEPSEEK_API_KEY` / `OPENCLAW_API_KEY`，`MINIMAX_API_KEY`（本项目 .env 中的唯一密钥）不在其中。
  3. **端点不匹配**：`DeepSeekChat` 硬编码 DeepSeek 端点与模型，即便加载到 MiniMax 密钥也会 401。
  4. **静默降级**：`graph_builder` 无密钥时仅打印一行提示，`web/app.py` / `run.py` 也只查项目根 `.env` → 服务能启动，但**专家评分全部返回「待评估」**。
  5. **提示依赖分数**：指导触发条件是「连续 2 轮低于 60 分」，而评分永远为「待评估」→ 分数既不达标也不计入 → **提示永不触发**（这是「完全没生效」的直接原因）。
- **功能范围：**
  1. **密钥加载加固**：`.env` 查找路径覆盖「项目根 + web/」；解析改用 `utf-8-sig` 并显式去除 BOM；环境变量接受 `DEEPSEEK_API_KEY` / `MINIMAX_API_KEY` / `OPENCLAW_API_KEY` / `LLM_API_KEY`；`web/app.py`（dotenv，双路径 + BOM 兼容）与 `run.py`（双路径手工解析 + BOM 兼容）同步修正。
  2. **端点与模型可配**：新增 `get_llm_endpoint()`；`LLM_BASE_URL` / `LLM_MODEL` / `LLM_PROVIDER` 覆盖优先，否则按密钥来源取默认值（DeepSeek / MiniMax OpenAI 兼容端点）。
  3. **不可用显式告警**：`graph_builder` 无密钥时打印已检查的 `.env` 路径与影响范围；专家「待评估」区分原因（无密钥 / 输出无法解析 / 结构不合法），反馈与推荐语直接给出原因，不再笼统显示「待评估」。
  4. **提示不再依赖分数**：新增「未获得有效评分」连败计数——连续 2 轮未获有效评分时同样展示**基于本轮情境**的策略提示（与低分触发的维度级提示区分表述）；无评分不触发「不及格」预警。
- **边界条件：** 无评分提示仅给情境策略（不含可照抄话术）；预警仍只针对「已评分且低于阈值」；环境变量优先级高于 `.env`；端点覆盖项缺失时按密钥来源兜底。
- **验收标准：** ①带 BOM 的 `web/.env` 可被正确解析并取到密钥（`tests/test_llm_config.py` 5 项）；②连续 2 轮待评估 → 触发情境提示且不触发低分预警（`tests/test_coaching.py` 新增用例）；③第 1 次待评估即显示「专家评分未配置 API 密钥…」与「再连续 1 轮将显示基于本轮情境的提示」；④第 2 次待评估时卡面与写作提示出现且不含可照抄话术（浏览器实测）。

## R18 指导呈现不可见问题修复（2026-11-05）

- **现象：** 后端触发条件已满足（真实会话实测评分序列 25.0 / 33.6 / 37.1，连续 3 轮低于 60，`coaching` 正常下发），但用户仍看不到任何指导卡面。

- **功能范围：**
  1. **窄屏不再隐藏干预区**：≤768px 时左侧栏隐藏、右侧干预区改为置顶显示（`order: -1`）。

- **边界条件：** 浮层挂在 `document.body`（不受应用容器显隐影响）；对话流卡片仅在指导内容非空时插入；徽标计数随会话累加，重置会话时归零。
- **验收标准：** 浏览器实测（700px 窄屏 + 模拟进行中）：右侧干预区、对话流指导卡、顶部浮层、面板内指导卡、发送状态条**五处全部可见**；徽标显示「指导 ×1」。

## R27 自动停止：澄清「百分制」疑问并移除压力/风险硬门槛（2026-11-09）

### 一、回答：不是百分制 vs 小数导致的

内部状态**统一为 0–1 小数**（`bullying_intensity` 取值 0.0–1.0，5% 即 0.05），终止判定的阈值也是 0–1（`bullying_intensity_max: 0.20` 即 20%）；仅在**前端显示层**把 0–1 乘以 100 显示为百分比。全程无单位错配，「改为百分制」不是不停止的原因。

### 二、真正的根因（结合用户场景实测定位）

R26 的「欺凌行为停止」出口仍要求四个条件**同时**满足：

```
attack_frequency < 0.20 且 bullying_intensity < 0.20 且 victim_distress < 0.50 且 retaliation_risk < 0.30
```

用户场景：用「坚定制止」把欺凌强度压到 5% 以下（前两项达标），但**受害者压力 `victim_distress` 仍 ≥ 50%**（教师只制止未安抚，或压力靠自然衰减过慢）→ 第三项永假 → 计数不累计 → 永不自动停止、只能超时。`retaliation_risk ≥ 0.30`（如采用了对质类话术）同理会卡住。

### 三、修复（重构停止判定，压力/风险不再阻塞停止）

「欺凌行为停止」**只以可观测的欺凌指标为准**（`bullying_intensity < 0.20` 且 `attack_frequency < 0.20`，二者强相关），连续 3 轮即停止；`victim_distress` / `retaliation_risk` 从「停止门槛」改为「结束文案分类」——如实提示未完成项，但不再阻塞收敛：

- 压力仍未恢复 → 「欺凌行为已连续 3 轮停止，但受害者压力仍未恢复（60%），请继续关注安抚与支持。」
- 报复风险仍存 → 「…但仍存在报复风险，请注意隔离与后续跟进。」
- 教师跟进不足 → 「…教师保护与跟进记录不足，按实际干预评分。」
- 全部达标 → 「欺凌现象停止，调解成功。」

（result_type 均 success，教师干预质量仍由报告端独立评分，教学评价不受影响）
